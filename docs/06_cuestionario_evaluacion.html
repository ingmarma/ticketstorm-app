Pregunta 1
Describe de manera detallada cómo tu sistema está protegido contra overbooking
Defensa en profundidad — 4 capas independientes

El overbooking en TicketStorm es imposible por diseño, no por convención. La estrategia es defense in depth: cuatro capas independientes, cada una capaz de prevenir overbooking por sí sola. Si una falla, las otras tres lo capturan. Las capas operan en orden de latencia ascendente — rechazamos rápido en Redis antes de tocar la base de datos.

1
Capa 1 — Lua script atómico en Redis
EVAL · BITMAP · ~0.5ms latencia

La disponibilidad de asientos vive en Redis como un bitmap por sección (un bit por asiento: 0=disponible, 1=ocupado). El check-and-set se hace con un Lua script ejecutado atómicamente por Redis — entre el GETBIT y el SETBIT no puede ejecutarse ningún otro comando. Race condition matemáticamente imposible en esta capa.

reserve_seat.lua — atómico por contrato RedisLua
local bit_value = redis.call('GETBIT', KEYS[1], ARGV[1])
if bit_value == 0 then
    redis.call('SETBIT', KEYS[1], ARGV[1], 1)
    return 1  -- éxito: asiento reservado
else
    return 0  -- falla: asiento ya ocupado, rechazar
end

Para un venue de 50k asientos el bitmap ocupa ~6.25KB. BITPOS permite encontrar el primer asiento disponible en O(N) sobre bytes — practicamente instantáneo.

2
Capa 2 — Distributed Lock (Redisson Redlock)
Redlock N=3 quorum=2 · TTL 5s · ~2ms latencia

Antes de escribir el evento SeatReserved en PostgreSQL, adquirimos un distributed lock con Redisson implementando el algoritmo Redlock sobre 3 nodos Redis independientes. El lock requiere quorum de 2 nodos para considerarse válido. TTL del lock: 5 segundos (suficiente para completar la operación). Si no se puede adquirir, retorno HTTP 503 y el cliente reintenta.

El lock token es un UUID único por cliente, validado en el unlock vía Lua script — esto previene que el cliente A libere el lock del cliente B si su operación tardó demasiado y el lock ya había expirado y sido re-adquirido.

3
Capa 3 — Pessimistic locking en PostgreSQL
SELECT FOR UPDATE · DB-level guard · ~5ms latencia

Dentro de la transacción que escribe el evento SeatReserved, hacemos SELECT FOR UPDATE sobre la fila del asiento en seat_projections. Esto bloquea cualquier otra transacción que intente leer-para-modificar el mismo asiento hasta que commiteemos.

Esta capa cubre el caso (extremadamente improbable) de que Redis falle por completo — el sistema sigue siendo correcto a costa de mayor latencia, porque PostgreSQL se convierte en el único árbitro.

4
Capa 4 — UNIQUE constraint sobre Event Sourcing
CONSTRAINT uq_aggregate_version · última guardia

El Event Store de Inventory tiene una constraint UNIQUE (aggregate_id, aggregate_version). Si por algún bug catastrófico llegasen dos comandos a escribir la versión N+1 del mismo asiento, PostgreSQL rechaza el segundo con 23505 unique_violation.

Esta es la capa de "última línea de defensa": nunca debería activarse en operación normal, pero si lo hace, el sistema sigue siendo correcto y emitimos una alerta crítica en Grafana para investigación de raíz.

Garantías adicionales por Event Sourcing

El estado de cada asiento no es una columna mutable en una tabla; es la proyección del log inmutable de eventos. No existe UPDATE seats SET status='RESERVED' en el sistema. Solo existe INSERT INTO inventory_events (event_type='SeatReserved', ...). Esto elimina toda una clase de bugs de race conditions en updates.

El invariante de dominio es: nunca pueden existir dos eventos SeatReserved activos para el mismo asiento. Un evento se considera "activo" si no ha sido seguido por SeatReleased o SeatPurchased. La proyección a seat_projections es eventualmente consistente con el log de eventos, pero el log es la fuente de verdad — si hay discrepancia, regeneramos la proyección desde el log.

Manejo de expiración de reservas (TTL)

Cuando una reserva temporal expira (10 minutos sin pago), los asientos deben liberarse automáticamente. Esto se hace vía Redis keyspace notifications: cada reserva tiene una key reservation:ttl:{id} con EXPIRE 600. Cuando Redis emite el evento expired, un listener en Reservation Service consume y emite ReservationExpired en Kafka. Inventory consume ese evento y libera los asientos atravesando las mismas 4 capas en sentido inverso (Lua: SETBIT a 0, emit SeatReleased).

Resumen. Cuatro capas independientes hacen el overbooking imposible: Redis Lua atómico (rechazo rápido), Redlock distribuido (consistencia cross-instance), Postgres pessimistic lock (DB-level guard), UNIQUE constraint sobre Event Store (última guardia). Event Sourcing elimina la clase entera de bugs por estado mutable. Las reservas expiradas se liberan automáticamente vía Redis keyspace notifications.
Pregunta 2
Explica en qué partes del diseño de tu sistema integrarás capacidades resilientes, y de qué forma
Filosofía: fail fast, recover gracefully

La resiliencia en TicketStorm está integrada en cada interacción cross-component, no agregada como afterthought. Toda llamada externa (red, gateway, DB, cache) usa al menos uno de estos patrones: Circuit Breaker, Retry con exponential backoff, Bulkhead, TimeLimiter, RateLimiter, o Fallback. La librería principal es Resilience4j, configurada declarativamente con annotations en Spring Boot.

Circuit Breaker — el patrón más importante

Cada servicio downstream tiene su circuit breaker configurado. Cuando un servicio comienza a fallar (ej: gateway de pago caído), el circuit breaker se abre y rechaza llamadas inmediatamente sin esperar timeout — esto previene el efecto dominó donde un servicio lento consume threads del caller y propaga la degradación. Sin circuit breaker, un fallo en Stripe podría tumbar todo el sistema de checkout en cascada.

Retry con exponential backoff + jitter

Los reintentos solo se aplican a operaciones idempotentes o que tengan idempotency key. Exponential backoff con jitter (random component) previene "thundering herd" cuando un servicio se recupera y miles de clientes reintentan simultáneamente.

Resilience4j config — Payment retryYAML
resilience4j.retry:
  instances:
    payment-gateway:
      max-attempts: 4
      wait-duration: 1s
      exponential-backoff-multiplier: 2     # 1s → 2s → 4s → 8s
      randomization-factor: 0.5             # jitter ±50%
      retry-exceptions:
        - org.springframework.web.client.ResourceAccessException
        - java.net.SocketTimeoutException
      ignore-exceptions:
        - com.ticketstorm.payment.FraudRejectedException  # no reintentar
        - com.ticketstorm.payment.InsufficientFundsException
Bulkhead — aislamiento de recursos

El patrón Bulkhead aísla pools de threads por tipo de operación crítica. Si las llamadas a Stripe se vuelven lentas, no consumen los threads disponibles para el resto del sistema. Implementación: ThreadPoolBulkhead de Resilience4j separa pools por servicio downstream.

  • Payment Service: 50 threads para gateway externo, 20 para fraud scorer, 30 para DB queries
  • Reservation Service: 100 threads para Inventory calls, 50 para DB
  • Catalog Service: 80 threads ES, 40 fallback DB — separación crítica durante incidentes
TimeLimiter — fail fast

Cada llamada externa tiene timeout estricto. Sin TimeLimiter, una request "colgada" puede ocupar un thread indefinidamente. Configuración:

  • Payment gateway: 5 segundos (alineado con SLO checkout p99 < 500ms compuesto)
  • Vertex AI: 10 segundos (RAG con embedding generation puede tardar)
  • DB queries: 3 segundos (cualquier query más lenta indica problema)
  • Redis operations: 200ms (estructuras simples deben ser sub-100ms)
Outbox Pattern — resiliencia de eventos

Sin Outbox, hay riesgo de inconsistencia: la transacción DB commit, pero el envío a Kafka falla → otros servicios nunca se enteran del cambio. Outbox lo previene: el evento se escribe en una tabla outbox_events en la misma transacción que el state change. Un worker separado lee la tabla y publica a Kafka. Si Kafka está caído, el worker reintenta indefinidamente sin afectar la operación principal. Garantía: at-least-once delivery (consumers son idempotentes).

Saga compensatoria — resiliencia de transacciones distribuidas

En un flujo distribuido (Reservation → Inventory → Payment), si un paso falla en el medio, los pasos anteriores deben revertirse. El Saga coreografiado lo automatiza: si PaymentFailed es emitido, Inventory consume el evento y emite SeatReleased (compensación). Esto evita estado inconsistente sin requerir un orquestador central.

Dead Letter Topics — resiliencia ante poison messages

Cada topic Kafka crítico tiene un Dead Letter Topic (DLT) asociado. Si un consumer falla N veces procesando un mensaje (ej: payload corrupto, bug), el mensaje se envía al DLT en lugar de bloquear el partition. Esto previene que un mensaje "venenoso" detenga el procesamiento. Grafana alerta cuando un DLT recibe mensajes — investigación manual.

Multi-zone deployment + DR multi-cloud

GKE Autopilot multi-zone us-central1-a/b/c con PodAntiAffinity distribuye pods entre zonas — pérdida de una zona no afecta el servicio. PostgreSQL Cloud SQL en alta disponibilidad regional (primary + standby). Redis Memorystore replicado entre zonas. Disaster Recovery: replica asíncrona del Event Store a OCI (Oracle Cloud) — si GCP us-central1 cae completo, podemos hacer failover a OCI con RPO < 5 minutos.

Pregunta 3
Explica el uso de concurrencia en tu sistema, si es aplicable
Tres modelos de concurrencia, uno por caso de uso

TicketStorm usa tres modelos de concurrencia distintos, cada uno seleccionado según el patrón del workload. No hay un modelo único óptimo para todo el sistema — la decisión por servicio es deliberada.

A
Virtual Threads (Java 21 Project Loom) — para I/O blocking
Catalog, Inventory, Reservation, Payment, Notification

El cambio más impactante en Java de la última década. Un Virtual Thread cuesta ~1KB de memoria vs ~1MB de un platform thread. Permite escribir código blocking (try/catch, synchronous I/O) sin penalización de concurrencia. Spring Boot 3 con spring.threads.virtual.enabled=true usa VTs para el servlet container — cada request HTTP corre en su propio Virtual Thread.

Por qué Virtual Threads y no WebFlux para estos servicios: el código de negocio (transacciones DB, llamadas HTTP, queries Kafka) es naturalmente imperativo. WebFlux exige Reactor (Mono/Flux) que es ergonómicamente costoso, debugging difícil, stack traces ilegibles. Virtual Threads dan la mayoría del beneficio (alta concurrencia) sin el costo (cambio de modelo mental).

Reservation Service — código blocking simple, alta concurrenciaJava 21
@RestController
public class ReservationController {

    @PostMapping("/v1/reservations")
    public ReservationResponse create(@RequestBody CreateRequest req) {
        // Spring asigna un Virtual Thread a este request automáticamente.
        // Cada operación blocking (DB, Kafka, HTTP) suspende el VT, no el carrier.
        var seats = inventoryClient.checkAvailability(req.eventId(), req.items());
        var reservation = repository.save(new Reservation(req));
        kafkaTemplate.send("tickets.reserved", reservation.toEvent());
        return ReservationResponse.from(reservation);
    }
}

Caveat técnico: bloques synchronized hacen "pinning" del Virtual Thread al carrier thread (no se desmonta). Solución: reemplazar con ReentrantLock. ThreadLocals también son costosos (memoria por VT). El equipo está entrenado en estas restricciones.

B
Reactive (Spring WebFlux + Reactor) — para streams con backpressure
Virtual Queue Service (WebSocket de 5M conexiones)

El Virtual Queue Service mantiene WebFlux porque el caso de uso lo justifica: 5M conexiones WebSocket simultáneas con backpressure explícito al pushear updates de posición. Reactor gestiona elegantemente la composición de streams (Redis pub/sub → filter por user → WebSocket sink).

Virtual Threads serían viables aquí también, pero el modelo reactivo de Reactor encaja mejor con la naturaleza streaming del caso de uso: no solo se trata de N requests independientes, sino de un long-lived stream por usuario con eventos asíncronos del sistema.

VirtualQueueController — WebFlux reactive WebSocketReactor
@Component
public class QueueWebSocketHandler implements WebSocketHandler {

    @Override
    public Mono<Void> handle(WebSocketSession session) {
        var eventId = extractEventId(session);
        var userId = extractUserId(session);

        var positionUpdates = queueService.streamPositionUpdates(eventId, userId)
            .map(pos -> Json.toJson(new PositionUpdate(pos.position(), pos.totalInQueue())))
            .map(session::textMessage)
            .onBackpressureBuffer(100, BufferOverflowStrategy.DROP_OLDEST);

        return session.send(positionUpdates);
    }
}
C
Structured Concurrency (JEP 453) — fan-out paralelo
Inventory Service — verificación paralela de N asientos

Cuando un usuario reserva múltiples asientos (ej: 4 tickets), debemos verificar disponibilidad de los 4 en paralelo, no secuencialmente. Structured Concurrency (estable en Java 25, preview en 21) permite fan-out con cleanup automático: si una sub-task falla, las demás se cancelan automáticamente.

InventoryService — verificación paralela de seatsJEP 453
public List<SeatAvailability> checkBatch(List<UUID> seatIds) {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        var futures = seatIds.stream()
            .map(id -> scope.fork(() -> checkSingleSeat(id)))
            .toList();
        scope.join().throwIfFailed();
        return futures.stream().map(Subtask::get).toList();
    }
}

Trade-off vs CompletableFuture: structured concurrency garantiza que ninguna task queda huérfana si el caller se cancela. Más seguro por contrato.

D
Kafka Streams — concurrencia distribuida
Agregaciones en tiempo real

Kafka Streams paraleliza naturalmente por partición. Aplicaciones de Streams (ej: contador de tickets vendidos por segundo, revenue dashboard) consumen N particiones en N threads. Escalado horizontal automático: si agregamos instancias de la app, Kafka redistribuye particiones via consumer rebalance.

Coordinación de concurrencia en operaciones críticas

Más allá del modelo de threading, la coordinación entre instancias de un servicio es clave:

  • Redisson Redlock coordina acceso concurrente a asientos entre instancias del Inventory Service
  • Optimistic locking en Event Store via UNIQUE(aggregate_id, version) — concurrencia segura sin locks pesimistas a nivel app
  • Kafka exactly-once con transactional producers — coordinación entre commit DB y publish Kafka es atómica
  • Atomic operations en Redis (Lua scripts, INCR, ZADD) — operaciones lock-free single-threaded por design de Redis
Resumen. Modelo de concurrencia híbrido por caso de uso. Virtual Threads (Java 21) para los servicios I/O-bound (4 de 7), permitiendo código simple sin sacrificar throughput. WebFlux reactive solo donde el streaming con backpressure lo justifica (Virtual Queue). Structured Concurrency para fan-out paralelo con cleanup automático. Kafka Streams para procesamiento distribuido. Coordinación entre instancias via Redisson Redlock, optimistic locking en Event Store, y operaciones atómicas Redis.
Pregunta 4
¿Cómo planeas manejar la llegada masiva de usuarios en un evento extremadamente popular?
El problema: 5M usuarios concurrentes en T=0

Cuando se abre la venta de un evento masivo (ej: Taylor Swift), millones de usuarios golpean el sistema simultáneamente. Sin diseño específico, los efectos son catastróficos: thread pools saturados, DB connections agotadas, downstream services en cascada. La solución no es "escalar más" — es desacoplar el spike del sistema de reservaciones mediante una fila virtual.

Fila virtual — el patrón central

El concepto: al abrir la venta, los usuarios no llegan directamente al checkout. Llegan a una fila virtual donde reciben un token de posición. El Inventory Service procesa la fila a un ritmo controlado (ej: 1000 usuarios/segundo). Los usuarios reciben notificación cuando es su turno. Esto convierte un spike de 5M concurrentes en un flujo sostenido manejable.

1
Pre-event — preparación T-30min

30 minutos antes de sale_opens_at, el sistema entra en modo "warm-up":

  • HPA pre-scale: GKE Autopilot escala proactivamente Queue Service a N pods esperados
  • Redis warming: bitmap de asientos pre-cargado en cache, evita cold start
  • CDN pre-warm: páginas del evento cacheadas en edge globales
  • Notification fan-out: 50M emails "la venta abre en 30 min" via GCP Pub/Sub
  • Cloud Armor: reglas DDoS endurecidas, rate limits temporales más estrictos por IP
2
T=0 — apertura de venta

5M usuarios envían POST /v1/queue/join en cuestión de segundos. El sistema absorbe el spike:

  • Cloud Load Balancer + Cloud Armor: absorbe el spike a nivel edge, rate limiting por IP
  • Spring Cloud Gateway: rate limiting adicional por userId (5 req/min)
  • Queue Service en Virtual Threads: cada request hace ZADD Redis y retorna en <100ms
  • Redis Sorted Set: ZADD queue:{eventId} NX {timestamp_us} {userId} — O(log N) — ~23 comparaciones para 5M usuarios
3
T+seconds — desacople via WebSocket

Una vez en la fila, el usuario no está haciendo polling al sistema de reservaciones. Está conectado a un WebSocket que pushea actualizaciones de posición. Esto desacopla completamente la espera del sistema crítico:

  • 5M WebSocket conexiones: Virtual Queue Service en Spring WebFlux + Virtual Threads
  • Updates cada 30s o cuando posición cambia significativamente (delta > 5%)
  • Worker pool procesa N usuarios/segundo hacia Reservation Service (configurable por evento: ej 500-2000 ups)
  • El usuario puede cerrar la app: cuando es su turno, recibe push notification — no necesita estar mirando la pantalla
4
Turno del usuario — AccessToken JWT

Cuando el worker promueve al usuario al frente de la fila, le emite un AccessToken JWT firmado RS256 con TTL de 15 minutos. Este token es requerido en el header X-Queue-Access-Token al hacer POST /v1/reservations. Sin token válido → 401. Esto garantiza que:

  • Solo los usuarios autorizados llegan al checkout — el resto está esperando
  • El checkout opera a ritmo controlado — nunca más de N concurrentes
  • Token no renovable — si el usuario no completa en 15min, vuelve a la fila
Auto-scaling reactivo durante el evento

Backpressure y shedding

Si el ritmo de ingreso supera la capacidad incluso después de auto-scale, aplicamos load shedding proactivo: el Gateway retorna 503 con header Retry-After a un porcentaje de requests, priorizando usuarios ya en cola. Esto preserva la experiencia de quienes ya están dentro vs degradar todo el sistema.

Prevención de bots

Los eventos masivos atraen scalpers automatizados:

  • reCAPTCHA Enterprise en endpoint /queue/join — score < 0.5 → rechazo
  • Device fingerprinting: detección de browsers headless / patrones automatizados
  • Rate limiting agresivo: 5 join/min por userId, 1 conexión WS por (user, evento)
  • Fraud scoring AI: velocity, IP reputation, device, behavior — score alto → MFA forzado
  • Max tickets per user: hard limit a nivel evento (default 4)
Resumen. La estrategia central es fila virtual: convertir un spike de 5M concurrentes en un flujo controlado. Pre-event: HPA pre-scale, Redis warming, CDN warm. T=0: absorber spike en Gateway + Queue Service con Redis Sorted Set. T+seconds: desacoplar via WebSocket (usuario espera sin pollear). Auto-scaling con métricas custom (Kafka lag, WS connections). Load shedding si supera capacidad. Anti-bot con reCAPTCHA + fraud AI.
Pregunta 5
Describe tu análisis desde la perspectiva del CAP Theorem
CAP Theorem aplicado: no es decisión binaria, es por bounded context

El CAP Theorem de Eric Brewer establece que en presencia de una partición de red (P), un sistema distribuido debe sacrificar consistencia (C) o disponibilidad (A). P no es opcional — siempre puede haber partición. La elección real es entre CP (consistente pero indisponible durante partición) o AP (disponible pero potencialmente inconsistente).

TicketStorm no es un sistema único. Cada bounded context elige su posición en CAP según su criticidad de negocio. Esto es la decisión arquitectónica más importante del diseño.

CP
Servicios CP — Consistencia es no-negociable
Inventory Service: overbooking es inaceptable. Mejor que un usuario reciba "intente nuevamente" a vender el mismo asiento dos veces.

Reservation Service: el estado de reserva debe ser consistente. Una reserva creada exitosamente debe ser visible en lecturas subsiguientes.

Payment Service: exactly-once cobro es crítico. Idempotency keys garantizan consistencia incluso ante reintentos.
AP
Servicios AP — Disponibilidad gana sobre consistencia perfecta
Event Catalog: mostrar info de eventos levemente desactualizada (5-30s lag) es aceptable. Mejor a "no podemos mostrar el catálogo".

Virtual Queue: mostrar posición aproximada (off by 100) es aceptable. Critical: que el usuario sepa que está en cola.

Notification: at-least-once delivery aceptable (mejor recibir 2 emails que ninguno).

AI Discovery: embeddings ligeramente stale es aceptable. La búsqueda semántica no es time-sensitive.

Cómo se materializan las decisiones CP/AP
CP
Implementación de CP en Inventory + Reservation + Payment

Las 4 capas anti-overbooking son inherentemente CP. Si Redis falla, el sistema rechaza requests (HTTP 503) en lugar de servir datos inconsistentes. PostgreSQL es el source of truth — si la DB primaria está particionada del standby durante un failover, las escrituras se rechazan hasta que la red se restaura.

Concretamente: ante partición, el Inventory Service prefiere retornar 503 Service Unavailable antes que arriesgar overbooking. Esto se manifiesta como menor disponibilidad medida — pero la disponibilidad de un sistema con overbooking es 0 desde el punto de vista del negocio.

AP
Implementación de AP en Catalog + Queue + Notification

Event Catalog: CQRS read/write split. PostgreSQL es source of truth (CP). Elasticsearch y Redis son réplicas eventually consistent (AP). Si la replicación tiene lag de 5s, los usuarios pueden ver disponibilidad ligeramente desactualizada — aceptable, porque el Inventory Service (CP) es el que toma la decisión final al reservar.

Virtual Queue: Redis Cluster usa replicación asíncrona. Si un master falla durante un failover, puede haber pérdida de algunos ZADDs recientes (window de pocos segundos). Aceptable porque la posición exacta no es crítica — el usuario será re-encolado si pierde su slot, con UX explícita.

Notification: Kafka + Outbox garantizan at-least-once. Un usuario puede recibir 2 emails de confirmación si hay un retry del consumer — aceptable, vs el costo de garantizar exactly-once delivery (que es virtualmente imposible en sistemas distribuidos sin idempotencia del receiver).

PACELC — el complemento de CAP

PACELC (Daniel Abadi) extiende CAP: incluso sin partición, el sistema debe elegir entre latencia (L) y consistencia (C). Esta dimensión es más práctica que CAP porque las particiones son raras pero los trade-offs de latencia ocurren constantemente.

Decisión clave: dónde poner la "L de boundary" entre CP y AP

El diseño coloca la boundary CP/AP en el momento de la reserva. Antes (browse, search, queue): AP, baja latencia, alta disponibilidad. Después (reserve, pay): CP, consistencia estricta. Esta boundary es deliberada: los usuarios pueden navegar y esperar durante una degradación de catálogo, pero no deben poder iniciar transacciones inconsistentes.

Concretamente, esto significa que durante un incidente parcial:

  • Si Elasticsearch falla: el browse degrada (fallback a queries Postgres más lentas), pero el sistema sigue funcional
  • Si Redis falla: Inventory degrada en latencia (~50ms vs 2ms) pero sigue siendo correcto via Postgres
  • Si PostgreSQL primary falla: failover automático a standby. Read replicas siguen sirviendo durante failover. Window de 30-60s de unavailability del write side.
  • Si Kafka falla: Reservation/Payment siguen funcionando localmente, eventos se acumulan en Outbox. Cuando Kafka recupera, se publican backlog.
Resumen. TicketStorm es un sistema híbrido CAP: CP en Inventory, Reservation y Payment (consistencia es un requisito de negocio innegociable — no overbooking, no cobros duplicados). AP en Catalog, Queue, Notification y AI (disponibilidad y baja latencia priorizadas, eventual consistency aceptable). PACELC: misma división entre latencia y consistencia sin partición. La boundary CP/AP está colocada en el momento de la reserva — antes el sistema es AP, después CP. Esta decisión es la más fundamental del diseño.
