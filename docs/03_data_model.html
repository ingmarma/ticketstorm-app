TicketStorm — Data Model

Modelo de datos completo por bounded context. Incluye schemas PostgreSQL con tipos, constraints e índices; estructuras Redis con patrones de acceso; Event Store schema para Event Sourcing; y tabla pgvector para AI Discovery. Cada decisión justificada con trade-offs.

Patrón: CQRS Read/Write split. Write-side en PostgreSQL (fuente de verdad). Read-side replicada en Elasticsearch (full-text + faceted search) y Redis (caché de páginas de eventos). El Catalog Service es AP en CAP — los resultados de búsqueda pueden ser levemente desactualizados. Acceptable para browse; no para disponibilidad de asientos.

Patrón: Event Sourcing puro. El estado de cada asiento se deriva exclusivamente del log de eventos en inventory_events. No hay columna status mutable — el status actual es una proyección. La tabla seat_projections es un read model materializado para queries de disponibilidad. CP en CAP: consistencia garantizada por 3 capas (Lua + Redlock + SELECT FOR UPDATE).

inventory_db — PostgreSQL (Cloud SQL) Event Store + Projections 
-- ─────────────────────────────────────────────
-- INVENTORY_EVENTS  (Event Store — inmutable)
-- ─────────────────────────────────────────────
CREATE TABLE inventory_events (
    id              BIGSERIAL       PRIMARY KEY,          -- sequence global para ordering
    aggregate_id    UUID            NOT NULL,              -- seat_id
    event_id        UUID            NOT NULL,              -- FK lógico a Catalog BC
    event_type      VARCHAR(80)     NOT NULL,              -- SeatReserved|SeatReleased|SeatPurchased
    aggregate_version INTEGER       NOT NULL,              -- optimistic concurrency por seat
    payload         JSONB           NOT NULL,              -- datos del evento
    correlation_id  UUID,                                  -- traceId para correlación
    causation_id    UUID,                                  -- id del comando que causó el evento
    occurred_at     TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_aggregate_version UNIQUE (aggregate_id, aggregate_version)
    -- La constraint UNIQUE (aggregate_id, aggregate_version) es la 3ra capa
    -- anti-overbooking: si dos transacciones intentan escribir version=N
    -- para el mismo asiento, una fallará con constraint violation.
);
CREATE INDEX idx_inv_events_aggregate  ON inventory_events (aggregate_id, aggregate_version);
CREATE INDEX idx_inv_events_event_id   ON inventory_events (event_id);
CREATE INDEX idx_inv_events_type       ON inventory_events (event_type, occurred_at);
CREATE INDEX idx_inv_events_corr       ON inventory_events (correlation_id);

-- ─────────────────────────────────────────────
-- SEAT_PROJECTIONS  (Read model materializado)
-- Se actualiza via projection handler al consumir inventory_events
-- ─────────────────────────────────────────────
CREATE TABLE seat_projections (
    seat_id         UUID            PRIMARY KEY,
    event_id        UUID            NOT NULL,
    category_id     UUID            NOT NULL,
    section_id      VARCHAR(50)     NOT NULL,
    row_label       VARCHAR(10),
    seat_number     SMALLINT,
    status          seat_status     NOT NULL DEFAULT 'AVAILABLE',
    reserved_by     UUID,           -- user_id si RESERVED
    reserved_until  TIMESTAMPTZ,   -- expiry de la reserva temporal
    last_event_seq  BIGINT          NOT NULL,              -- último evento aplicado
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_seat_proj_event       ON seat_projections (event_id, status);
CREATE INDEX idx_seat_proj_avail       ON seat_projections (event_id) WHERE status = 'AVAILABLE';
CREATE INDEX idx_seat_proj_reserved_by ON seat_projections (reserved_by) WHERE reserved_by IS NOT NULL;

-- ─────────────────────────────────────────────
-- INVENTORY_SNAPSHOTS  (performance: evita replay de todos los eventos)
-- Snapshot cada 100 eventos por aggregate_id
-- ─────────────────────────────────────────────
CREATE TABLE inventory_snapshots (
    aggregate_id    UUID            NOT NULL,
    version         INTEGER         NOT NULL,
    state           JSONB           NOT NULL,  -- snapshot del estado del aggregate
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    PRIMARY KEY (aggregate_id, version)
);

-- ENUMs
CREATE TYPE seat_status AS ENUM ('AVAILABLE', 'RESERVED', 'PURCHASED', 'BLOCKED');

-- PAYLOAD examples:
-- SeatReserved:  {"seat_id":"...","user_id":"...","reservation_id":"...","expires_at":"..."}
-- SeatReleased:  {"seat_id":"...","reason":"EXPIRED|PAYMENT_FAILED|USER_CANCELLED"}
-- SeatPurchased: {"seat_id":"...","user_id":"...","ticket_id":"...","payment_id":"..."}

Patrón: Event Sourcing + Outbox. El Reservation Service usa su propio Event Store. El patrón Outbox garantiza que los eventos de dominio se publiquen en Kafka si y solo si la transacción DB commit. Sin Outbox existe riesgo de que la DB commit pero Kafka falle, dejando la Saga en estado inconsistente.

reservation_db — PostgreSQL (Cloud SQL) Event Store + Outbox + Saga 
-- ─────────────────────────────────────────────
-- RESERVATION_EVENTS  (Event Store)
-- ─────────────────────────────────────────────
CREATE TABLE reservation_events (
    id                  BIGSERIAL       PRIMARY KEY,
    aggregate_id        UUID            NOT NULL,  -- reservation_id
    aggregate_version   INTEGER         NOT NULL,
    event_type          VARCHAR(80)     NOT NULL,
    -- ReservationCreated | ReservationExpired | TicketPurchased | ReservationCancelled
    payload             JSONB           NOT NULL,
    user_id             UUID            NOT NULL,
    event_id            UUID            NOT NULL,  -- FK lógico al Catalog BC
    correlation_id      UUID,
    causation_id        UUID,
    occurred_at         TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    CONSTRAINT uq_res_aggregate_version UNIQUE (aggregate_id, aggregate_version)
);
CREATE INDEX idx_res_events_aggregate ON reservation_events (aggregate_id, aggregate_version);
CREATE INDEX idx_res_events_user      ON reservation_events (user_id, occurred_at DESC);
CREATE INDEX idx_res_events_event_id  ON reservation_events (event_id);

-- ─────────────────────────────────────────────
-- RESERVATION_PROJECTIONS  (Read model)
-- ─────────────────────────────────────────────
CREATE TABLE reservation_projections (
    id              UUID            PRIMARY KEY,  -- reservation_id
    user_id         UUID            NOT NULL,
    event_id        UUID            NOT NULL,
    status          reservation_status NOT NULL,
    items           JSONB           NOT NULL,  -- [{seat_id, category_id, price, currency}]
    total_amount    NUMERIC(10,2)   NOT NULL,
    currency        CHAR(3)         NOT NULL DEFAULT 'USD',
    expires_at      TIMESTAMPTZ     NOT NULL,  -- created_at + 10 minutes
    idempotency_key UUID            UNIQUE,    -- para Payment Service
    last_event_seq  BIGINT          NOT NULL,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_res_proj_user       ON reservation_projections (user_id);
CREATE INDEX idx_res_proj_event      ON reservation_projections (event_id);
CREATE INDEX idx_res_proj_expires    ON reservation_projections (expires_at)
    WHERE status = 'PENDING';  -- partial index: solo reservas activas

-- ─────────────────────────────────────────────
-- OUTBOX  (Transactional Outbox Pattern)
-- INSERT en misma transacción que reservation_events.
-- Worker lee y publica en Kafka, luego marca published=TRUE.
-- ─────────────────────────────────────────────
CREATE TABLE outbox_events (
    id              BIGSERIAL       PRIMARY KEY,
    aggregate_id    UUID            NOT NULL,
    aggregate_type  VARCHAR(50)     NOT NULL DEFAULT 'Reservation',
    event_type      VARCHAR(80)     NOT NULL,
    kafka_topic     VARCHAR(120)    NOT NULL,
    payload         JSONB           NOT NULL,
    kafka_key       VARCHAR(100)    NOT NULL,  -- event_id para particionamiento
    published       BOOLEAN         NOT NULL DEFAULT FALSE,
    published_at    TIMESTAMPTZ,
    retry_count     SMALLINT        NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_outbox_unpublished ON outbox_events (created_at)
    WHERE published = FALSE;  -- partial index: solo pendientes

Patrón: Idempotency Keys + Outbox. La tabla idempotency_keys garantiza que reintentos de pago (por network failures, timeouts, etc.) no generen cobros duplicados. El idempotency_key es generado por el Reservation Service al crear la reserva y pasado como parte del comando de pago.

payment_db — PostgreSQL (Cloud SQL) Idempotency + Outbox 
-- ─────────────────────────────────────────────
-- PAYMENTS  (Aggregate Root)
-- ─────────────────────────────────────────────
CREATE TABLE payments (
    id                  UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    reservation_id      UUID            NOT NULL UNIQUE,  -- 1:1 con Reservation
    user_id             UUID            NOT NULL,
    idempotency_key     UUID            NOT NULL UNIQUE,  -- de Reservation Service
    amount              NUMERIC(10,2)   NOT NULL CHECK (amount > 0),
    currency            CHAR(3)         NOT NULL,
    status              payment_status  NOT NULL DEFAULT 'PENDING',
    -- PENDING | PROCESSING | SUCCESS | FAILED | REFUNDED
    gateway             VARCHAR(30)     NOT NULL,        -- 'STRIPE' | 'PAYU'
    gateway_payment_id  VARCHAR(200)    UNIQUE,          -- ID externo del gateway
    gateway_response    JSONB,                            -- raw response para auditoría
    fraud_score         DECIMAL(4,3),                     -- 0.000 - 1.000
    fraud_decision      VARCHAR(20),                      -- APPROVED | REJECTED | REVIEW
    failure_reason      VARCHAR(200),
    retry_count         SMALLINT        NOT NULL DEFAULT 0,
    processed_at        TIMESTAMPTZ,
    created_at          TIMESTAMPTZ     NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_payments_user        ON payments (user_id, created_at DESC);
CREATE INDEX idx_payments_status      ON payments (status) WHERE status = 'PENDING';
CREATE INDEX idx_payments_gateway_pid ON payments (gateway_payment_id) WHERE gateway_payment_id IS NOT NULL;

-- ─────────────────────────────────────────────
-- IDEMPOTENCY_KEYS  (exactly-once semántics)
-- Se consulta ANTES de procesar. Si ya existe → retorna cached result.
-- ─────────────────────────────────────────────
CREATE TABLE idempotency_keys (
    key             UUID            PRIMARY KEY,
    user_id         UUID            NOT NULL,
    operation       VARCHAR(50)     NOT NULL,   -- 'PROCESS_PAYMENT'
    request_hash    VARCHAR(64)     NOT NULL,   -- SHA-256 del request body
    response_status SMALLINT,                   -- HTTP status del resultado
    response_body   JSONB,                       -- respuesta cacheada
    payment_id      UUID            REFERENCES payments(id),
    expires_at      TIMESTAMPTZ     NOT NULL,   -- TTL: 24 horas
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_idemp_expires ON idempotency_keys (expires_at);  -- cleanup job
CREATE INDEX idx_idemp_user    ON idempotency_keys (user_id);

-- ─────────────────────────────────────────────
-- PAYMENT_OUTBOX  (mismo patrón que Reservation)
-- ─────────────────────────────────────────────
CREATE TABLE payment_outbox (
    id              BIGSERIAL       PRIMARY KEY,
    aggregate_id    UUID            NOT NULL,   -- payment_id
    event_type      VARCHAR(80)     NOT NULL,   -- PaymentProcessed | PaymentFailed | PaymentRefunded
    kafka_topic     VARCHAR(120)    NOT NULL,
    payload         JSONB           NOT NULL,
    kafka_key       VARCHAR(100)    NOT NULL,
    published       BOOLEAN         NOT NULL DEFAULT FALSE,
    published_at    TIMESTAMPTZ,
    retry_count     SMALLINT        NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_payment_outbox_pending ON payment_outbox (created_at) WHERE published = FALSE;

-- ENUM
CREATE TYPE payment_status AS ENUM ('PENDING', 'PROCESSING', 'SUCCESS', 'FAILED', 'REFUNDED');

Redis Cluster (GCP Memorystore) — 6 nodos (3 master + 3 replica). Cada estructura de datos está diseñada para su patrón de acceso específico. Nomenclatura de keys: {dominio}:{entidad}:{id}. TTLs siempre definidos — ninguna key vive indefinidamente. AOF persistence habilitado para durabilidad.

Virtual Queue — Sorted Set
Una key por evento. Score = timestamp de ingreso (FIFO determinista)
queue:{eventId} → ZSET
ZADDZRANKZCARDZPOPMINZREM
Score: Unix timestamp en microsegundos (para desempate).
Member: userId (UUID string).
TTL: sale_closes_at + 1h (limpieza automática).
Complejidad: ZADD O(log N), ZRANK O(log N) — para 5M usuarios ~23 comparaciones.
Partición: clave incluye eventId → mismo nodo del cluster para todas las ops del evento.
Queue Access Tokens
JWT de acceso al checkout con TTL estricto
queue:token:{userId}:{eventId} → STRING
SET NXGETDELTTL
Value: JWT firmado RS256 con claims: {userId, eventId, queuePosition, iat, exp}.
TTL: 900 segundos (15 minutos). No renovable.
SET NX: garantiza que un usuario no puede tener dos tokens activos para el mismo evento.
Invalidación: DEL al completar reserva o al expirar.
Inventory — Seat Bitmap
Un bit por asiento. 0=disponible, 1=ocupado. O(1) check.
inventory:bitmap:{eventId}:{sectionId} → BITMAP
GETBITSETBITBITCOUNTBITPOSEVAL (Lua)
Índice del bit: seat_number dentro de la sección.
Lua script atómico (capa 1 anti-overbooking):
EVAL "if redis.call('GETBIT',KEYS[1],ARGV[1])=='0' then redis.call('SETBIT',KEYS[1],ARGV[1],'1') return 1 else return 0 end" 1 key seatIdx Capacidad: 1 byte = 8 asientos. Venue de 50k asientos = 6.25KB por sección.
TTL: event_date + 48h.
Reservation TTL
Expiración automática de reservas temporales en 10 minutos
reservation:ttl:{reservationId} → STRING
SET EXDELTTLKEYSPACE EVENT
Value: JSON con {reservationId, userId, eventId, seatIds[]}.
TTL: 600 segundos (10 minutos).
Keyspace notification: notify-keyspace-events Ex habilitado.
El Reservation Service escucha el evento expired y emite ReservationExpired en Kafka para liberar asientos.
Rate Limiting — Sliding Window
Por userId y por IP. Previene abuso del endpoint de reservas.
ratelimit:reserve:{userId} → STRING (contador) ratelimit:ip:{hashedIp} → STRING
INCREXPIREGET
Límites: 10 reservas/minuto por userId, 50 requests/minuto por IP.
Ventana: fixed window con EXPIRE 60s. Suficiente para protección; sliding window más costoso sin beneficio adicional aquí.
Respuesta al exceder: HTTP 429 con header Retry-After.
Distributed Lock — Redlock
Redisson Redlock sobre N=3 nodos independientes. Quorum=2.
lock:seat:{eventId}:{seatId} → STRING (lock token)
SET NX PXGET + EVALDEL (Lua)
TTL del lock: 5000ms (5 segundos — tiempo máximo de operación de reserva).
Value: UUID único por cliente — previene que un cliente libere el lock de otro.
Redlock: SET NX en 3 nodos independientes. Válido si ≥ 2 nodos responden y tiempo total < TTL/2.
Capa 2 anti-overbooking: operación atómica entre Lua script (Capa 1) y SELECT FOR UPDATE (Capa 3).
Event Catalog Cache
Cache-aside para páginas de eventos y disponibilidad agregada
catalog:event:{eventId} → STRING (JSON) catalog:availability:{eventId} → HASH
SET EXGETHGET/HSETDEL
catalog:event TTL: 300s (5 min). Invalidado en writes.
catalog:availability: HASH con fields {section_id → available_count}. TTL 30s — refresh frecuente para mostrar disponibilidad actualizada.
Cache-aside: miss → query DB → SET → return. El write invalida (DEL) no actualiza (evita stale write race).
User Session / Auth State
Estado de autenticación y preferencias de sesión
session:{userId} → HASH
HSETHGETALLEXPIREDEL
Fields: {last_active, active_reservations[], active_queue_events[], device_id, preferences}.
TTL: 3600s (1 hora de inactividad). EXPIRE se renueva en cada request.
Uso: verificar límite de reservas activas por usuario sin consultar DB en cada request.

Spring AI + pgvector + Vertex AI text-embedding-004. CREATE EXTENSION IF NOT EXISTS vector;

-- ─────────────────────────────────────────────
-- EVENT_EMBEDDINGS  (VectorStore de Spring AI)
-- Gestionada por Spring AI pgvector store abstraction
-- ─────────────────────────────────────────────
CREATE TABLE event_embeddings (
    id              UUID            PRIMARY KEY DEFAULT gen_random_uuid(),
    event_id        UUID            NOT NULL UNIQUE,   -- FK lógico a Catalog BC
    content         TEXT            NOT NULL,           -- texto vectorizado: nombre + desc + artistas + venue + tags
    embedding       vector(768)     NOT NULL,           -- text-embedding-004 output
    metadata        JSONB           NOT NULL DEFAULT '{}',
    -- metadata: {event_date, city, country, genre[], artists[], venue_name,
    --            status, sale_opens_at, price_min, price_max}

    updated_at      TIMESTAMPTZ     NOT NULL DEFAULT NOW()
);

-- Índice HNSW (Hierarchical Navigable Small World)
-- Mejor trade-off recall/latencia para búsqueda semántica de alta demanda.
-- ef_construction=128: mayor recall en build time.
-- m=16: 16 conexiones por nodo — balance entre memoria y recall.
CREATE INDEX idx_event_embeddings_hnsw
    ON event_embeddings USING hnsw (embedding vector_cosine_ops)
    WITH (ef_construction = 128, m = 16);

-- Índice en metadata para filtros pre-retrieval
-- (ej: buscar solo eventos PUBLISHED en un país)
CREATE INDEX idx_event_emb_metadata ON event_embeddings USING gin(metadata);
CREATE INDEX idx_event_emb_event_id ON event_embeddings (event_id);

Modelo de datos distribuido. En una arquitectura de microservicios con Event Sourcing, no existen JOINs entre bounded contexts. Las relaciones cross-BC son lógicas (UUIDs compartidos) no físicas (foreign keys). Cada servicio es dueño de su schema y su base de datos. Las referencias cross-BC se resuelven via eventos de dominio o llamadas de API explícitas.

Relaciones dentro del Event Catalog BC
events N : 1 venues Un evento pertenece a un venue. REFERENCES con FK real. ON DELETE RESTRICT
events N : N artists Un evento tiene múltiples artistas. Tabla pivot event_artists. Pivot: event_artists
events 1 : N ticket_categories Un evento tiene múltiples categorías de ticket (VIP, Campo, etc). ON DELETE CASCADE
Relaciones lógicas cross-BC (sin FK físico — via UUID compartido)
Catalog.events.id lógico Inventory.inventory_events.event_id Inventory es inicializado cuando Catalog emite EventPublished. Kafka event
Inventory.seat.id lógico Reservation.items[].seat_id Los items de una reserva referencian seats del Inventory BC. UUID compartido
Reservation.id lógico 1:1 Payment.reservation_id Un pago corresponde a exactamente una reserva. UNIQUE en Payment
Reservation.idempotency_key lógico 1:1 Payment.idempotency_keys.key Generado en Reservation, enviado a Payment como garantía de exactly-once. UUID en request header
Catalog.events.id lógico AI.event_embeddings.event_id Embedding generado al recibir EventCreated/Updated de Kafka. Kafka async
Resumen de bases de datos por bounded context
catalog_db PostgreSQL Cloud SQL. Tables: venues, artists, events, event_artists, ticket_categories CQRS write-side
inventory_db PostgreSQL Cloud SQL. Tables: inventory_events, seat_projections, inventory_snapshots Event Sourcing
reservation_db PostgreSQL Cloud SQL. Tables: reservation_events, reservation_projections, outbox_events, tickets Event Sourcing + Outbox
payment_db PostgreSQL Cloud SQL. Tables: payments, idempotency_keys, payment_outbox Idempotency + Outbox
Redis Cluster GCP Memorystore. Keys: queue SortedSet, access tokens, seat bitmaps, reservation TTL, rate limits, locks, cache Multi-BC
ai_db PostgreSQL + pgvector. Tables: event_embeddings (vector 768), conversation_sessions Spring AI VectorStore
