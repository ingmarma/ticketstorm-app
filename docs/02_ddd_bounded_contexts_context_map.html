El Context Map muestra las relaciones entre bounded contexts: U (Upstream) provee el modelo, D (Downstream) consume. Los patrones de integración determinan el tipo de acoplamiento. — Kafka async — gRPC/REST sync - - ACL (Anti-corruption Layer)
El lenguaje ubicuo (Ubiquitous Language) es el vocabulario compartido entre desarrolladores y expertos del dominio. Cada término tiene un significado preciso y único dentro de su bounded context. El mismo término puede tener significados diferentes en contextos distintos — esto es intencional en DDD.
Término Contexto Definición precisa en el dominio Diferencias inter-contexto
Event Catalog Concierto, festival o show en un venue específico con fecha y artistas definidos En Inventory es un "context" para el cual se gestiona disponibilidad de asientos
Seat Inventory Unidad atómica de disponibilidad. Puede ser asiento numerado o entrada general (un "slot") En Reservation es un ReservationItem — tiene precio y categoría asociada
Reservation Reservation Bloqueo temporal de uno o más asientos por 10 minutos para un usuario específico con AccessToken válido En el lenguaje de Payment es una "orden pendiente de pago"
AccessToken Queue JWT firmado emitido cuando el usuario llega al frente de la fila. Autoriza acceso al checkout por 15 minutos. No renovable. Distinto del JWT de autenticación de Keycloak — es un claim de posición de fila
Overbooking Inventory Estado prohibido en el que existen más SeatReserved activos que asientos físicos disponibles. El invariante de dominio más crítico del sistema. Término exclusivo del Inventory BC. Otros BCs no conocen este concepto directamente.
SaleWindow Catalog Ventana temporal durante la cual tickets de un evento están disponibles para compra. Tiene fecha/hora de apertura que dispara el evento de dominio SaleWindowOpened. SaleWindowOpened es el trigger que abre la Queue para ese eventId específico
FraudScore AI Discovery Valor Float [0.0, 1.0] generado por el modelo ML de Vertex AI. Representa probabilidad de fraude. Umbral de rechazo: 0.8 En Payment BC es un Value Object que determina si el pago procede o es rechazado
Queue Position Queue Rango del usuario en la fila (1-based). Calculado con ZRANK en Redis Sorted Set. Se actualiza en tiempo real via WebSocket push. Concepto exclusivo del Queue BC — ningún otro BC conoce posiciones de fila
IdempotencyKey Payment UUID único por intento de pago, enviado en header X-Idempotency-Key. Garantiza que reintentos no generen cobros duplicados. Patrón técnico — generado en Reservation y pasado a Payment como parte del comando
EventEmbedding AI Discovery Vector de dimensión 768 generado por text-embedding-004 de Vertex AI representando semánticamente el contenido de un evento (nombre, descripción, artistas, venue). Concepto exclusivo del AI BC. Catalog BC solo conoce el evento como entidad de negocio.
Saga coreografiado para el flujo de reserva y compra. Cada servicio publica eventos en Kafka — no hay orquestador central. Las líneas con fondo punteado en rojo son las transacciones compensatorias que se ejecutan si el pago falla.
