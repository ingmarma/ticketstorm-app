Convenciones globales
Content-Type: application/json (todas las requests/responses)
Auth header: Authorization: Bearer <JWT RS256 Keycloak>
Paginación: cursor-based con ?cursor=<opaque>&limit=20
IDs: UUID v4 en todos los recursos
Timestamps: ISO 8601 UTC (2026-07-01T18:00:00Z)
Rate limit headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset
Trace header: X-Trace-Id propagado en todas las responses (OpenTelemetry)
Versioning: URL-based /v1/. Breaking changes → /v2/

POST
/v1/queue/join
Unirse a la fila virtual de un evento. El usuario recibe su posición y queda en espera. Notificación WebSocket cuando es su turno.
Virtual Queue BC Redis ZADD
Security
JWT Bearer (Keycloak) — requerido
Rate limit: 5 req/min por userId
Request Body
POST /v1/queue/join
{
  "event_id": "evt_01j2k8p..."  // required — UUID del evento
}
Flujo interno
1
Verificar estado del evento
Catalog BC confirma que event.status = PUBLISHED y sale_opens_at ≤ NOW().
2
Verificar que usuario no está ya en fila
ZSCORE para verificar existencia. Si ya existe, retornar 409.
ZSCORE queue:{eventId} {userId}
3
ZADD atómico con timestamp
Score = Unix timestamp en microsegundos. NX flag: no sobreescribir si ya existe.
ZADD queue:{eventId} NX {timestamp_us} {userId}
4
Retornar posición y conectar WebSocket
ZRANK para posición actual. Response incluye URL del WebSocket para actualizaciones en tiempo real.

POST
/v1/reservations
Crear reserva temporal de asientos. Requiere AccessToken de la fila. 3 capas anti-overbooking. Reserva expira en 10 minutos.
Reservation BC Inventory BC CRÍTICO CP
Security
JWT Bearer (Keycloak)
Header X-Queue-Access-Token: <AccessToken de fila>
Rate limit: 10 req/min por userId
Request Headers
HeaderTipoRequeridoDescripción
AuthorizationstringrequeridoBearer <JWT Keycloak>
X-Queue-Access-TokenstringrequeridoAccessToken JWT recibido cuando el usuario llegó al frente de la fila. TTL 15min.
X-Idempotency-Keystring(UUID)recomendadoUUID único por intento. Si se omite, se genera en server. Para reintentos seguros.
Request Body
POST /v1/reservations
{
  "event_id": "evt_01j2k8p...",         // required
  "items": [                                // required — max 4 items
    {
      "seat_id": "seat_A1_001",            // Para asientos numerados
      "category_id": "cat_vip_..."
    },
    {
      "category_id": "cat_campo_..."        // Para entrada general — sin seat_id
    }
  ]
}
Flujo interno — 3 capas anti-overbooking
1
Validar X-Queue-Access-Token
Verificar firma RS256, TTL, que el eventId del token coincide con el request. Sin token válido → 401.
2
Capa 1: Lua script atómico en Redis
EVAL verifica bit=0 y setea bit=1 en una operación atómica. Si algún asiento ya está ocupado → 409.
EVAL lua_script 1 bitmap_key seatIndex
3
Capa 2: Distributed Lock (Redlock)
Adquirir Redisson Redlock para cada seat_id. TTL del lock: 5000ms. Si falla adquirir → 503.
4
Capa 3: SELECT FOR UPDATE en PostgreSQL
Pessimistic lock a nivel de DB antes de escribir el evento SeatReserved. UNIQUE constraint en (aggregate_id, version) como última guardia.
5
Crear ReservationCreated + Outbox atómico
INSERT en reservation_events y outbox_events en la misma transacción. SET Redis TTL 600s para la reserva.

POST
/v1/payments
Procesar el pago de una reserva activa. Incluye fraud scoring, idempotency guard y circuit breaker hacia gateway externo. Dispara Saga compensatoria si falla.
Payment BC Spring AI Fraud Idempotency
Security
JWT Bearer (Keycloak) — requerido
MFA verificado en Keycloak para este scope
Rate limit: 5 req/min por userId
Request Headers
HeaderTipoRequeridoDescripción
AuthorizationstringrequeridoBearer <JWT Keycloak con scope payments:write>
X-Idempotency-Keystring(UUID)requeridoUsar el idempotency_key devuelto por POST /reservations. Garantiza exactly-once.
Request Body
POST /v1/payments
{
  "reservation_id": "res_01j2...",       // required
  "payment_method": {
    "type": "CARD",                         // CARD | BANK_TRANSFER | WALLET
    "token": "tok_stripe_..."                // tokenizado en frontend (Stripe.js/PayU SDK)
    // NUNCA el PAN en texto plano — solo tokens del gateway
  },
  "billing_details": {
    "name": "Matias Martinez",
    "email": "matias@example.com",
    "country": "PY"
  }
}
Flujo interno
1
Idempotency check
Lookup de X-Idempotency-Key en tabla idempotency_keys. Si ya procesado → retornar respuesta cacheada inmediatamente.
2
Fraud scoring (Spring AI)
Llamada síncrona al AI Discovery Service → Vertex AI custom model. Features: velocity, IP reputation, device fingerprint, purchase history. Score > 0.8 → rechazo inmediato.
POST /internal/fraud/score → {score: 0.0-1.0, decision: APPROVED|REJECTED|REVIEW}
3
Verificar reserva activa
Reserva debe existir, pertenecer al usuario autenticado, y status = PENDING. TTL Redis debe ser > 0.
4
Llamada a gateway externo (Resilience4j)
Circuit breaker + retry exponencial (1s→2s→4s→8s, max 4 intentos). TimeLimiter: 5 segundos máximo. Fallback: encolar para procesamiento async.
5
Persistir + Outbox + emit Kafka
INSERT en payments + idempotency_keys + payment_outbox en una transacción. Kafka worker publica PaymentProcessed/PaymentFailed. Saga continúa o compensa.

GET /v1/events/{eventId} — Retorna el detalle completo de un evento incluyendo venue, artistas, categorías de ticket con disponibilidad en tiempo real (Redis HASH), y estado de venta. Misma estructura que los items de GET /v1/events pero con campos adicionales como sections del venue y timeline de la venta.
GET /v1/queue/status?event_id={eventId} — Retorna la posición actual del usuario autenticado en la fila. Usa ZRANK en Redis. Response idéntico al body del WS push message: {position, total_in_queue, estimated_wait_minutes, access_token (si es su turno)}. Complementario al WebSocket — para polling como fallback.
WebSocket wss://api.ticketstorm.io/ws/queue/{eventId} — Conexión permanente autenticada con ws_token del /queue/join. Mensajes del servidor: POSITION_UPDATE {position, total_in_queue, estimated_wait_minutes} (cada 30s o cuando cambia significativamente) y ACCESS_GRANTED {access_token, expires_at} (cuando es el turno del usuario). Spring WebFlux Reactor con Virtual Threads — soporta 5M conexiones concurrentes.
GET /v1/reservations/{reservationId} — Retorna estado actual de la reserva. Lee desde reservation_projections. Incluye: status (PENDING|PURCHASED|EXPIRED|CANCELLED), items con detalles de asientos, total_amount, expires_at y expires_in_seconds calculado como max(0, expires_at - NOW()). Útil para mostrar contador de tiempo al usuario.
GET /v1/payments/{paymentId} — Polling del estado de un pago PROCESSING. Lee desde payments table. Una vez que status = SUCCESS retorna lista de tickets con QR codes. Si status = FAILED retorna failure_reason. Recomendado polling cada 2s con max 15 intentos.
