TicketStorm — Tech Stack & Trade-off Analysis

Justificación de cada decisión arquitectónica del proyecto. Para cada componente: contexto, decisión final, alternativas consideradas, pros/contras, y trade-off explícito. Este documento es la base de las preguntas técnicas en revisión.

Contexto general. El sistema debe soportar 50M DAU con picos de 5M usuarios concurrentes. El cuello de botella tradicional en Java es el modelo de un thread por request, costoso (~1MB stack por platform thread). La elección del runtime y framework determina la capacidad de absorber estos picos sin saturar el thread pool.
Java 21 LTS + Virtual Threads (Project Loom)
Runtime principal del 100% de los microservicios
Runtime
Decisión

Java 21 LTS sobre Virtual Threads para todos los servicios I/O-bound. Reemplaza el modelo reactivo (WebFlux) en la mayoría de servicios, manteniendo código imperativo simple sin sacrificar concurrencia masiva.

Trade-off analysis
OpciónProsCons
Java 21 + Virtual Threads ✓ ~1KB por VT vs ~1MB platform thread. 5M conexiones viables. Código blocking simple. Synchronized blocks "pinnean" el carrier thread. ThreadLocal usage es costoso.
Java 17 + WebFlux reactivo Backpressure nativo. Reactor maduro. Streaming-first. Curva de aprendizaje alta. Debugging complejo. Stack traces ilegibles.
Kotlin Coroutines Coroutines suspend muy ergonómicas. Integración Spring buena. Equipo NFD S.A. ya domina Java. Cambio de lenguaje no justificado.
Justificación final

Excepción. El Virtual Queue Service mantiene WebFlux porque el caso de uso (5M WebSocket streams con backpressure de notificaciones) sí justifica el modelo reactivo: los Virtual Threads son excelentes para blocking I/O, pero WebFlux es superior cuando se necesita componer streams con backpressure explícito. Para el resto (Catalog, Inventory, Reservation, Payment, Notification), Virtual Threads gana por simplicidad sin perder throughput.

Spring Boot 3.x
Framework de aplicación con starters para todo el stack
Framework
Decisión

Spring Boot 3.x con spring.threads.virtual.enabled=true. Auto-configuración de Virtual Threads para Tomcat connector, @Async, y task executors. Stack maduro alineado con el ecosistema NFD S.A.

Trade-off vs alternativas
A favor de Spring Boot 3
  • Ecosistema maduro: Cloud Gateway, Security, Data, AI, Kafka, todos oficiales
  • Soporte nativo Virtual Threads + GraalVM native image
  • Spring AI 1.x con abstracciones VectorStore, ChatMemory, Advisors
  • Micrometer + OpenTelemetry integración automática
  • Equipo NFD S.A. ya productivo
Contras consideradas
  • Startup time mayor que Quarkus/Micronaut (~5-8s vs 1-2s)
  • Memoria base mayor (~200MB vs 80MB Quarkus)
  • Magic excesivo: auto-config puede ocultar problemas
  • Mitigable con GraalVM native image (startup < 100ms)
Trade-off explícito

Quarkus es objetivamente mejor en footprint y startup time, crítico para escalado serverless. Pero la productividad del equipo y el ecosistema (Spring AI, Spring Cloud Gateway, Spring Data) compensa. Para escalado masivo se planea migrar a GraalVM native image en Notification Service (workers efímeros donde startup importa).

Estrategia polyglot persistence. Cada bounded context elige su DB según su patrón de acceso. PostgreSQL es la default para sistemas con Event Sourcing (transaccionalidad, JSONB para payloads). Redis cubre los casos de baja latencia y estructuras especializadas. Elasticsearch para búsqueda full-text. pgvector para AI.
PostgreSQL 16 — Cloud SQL
DB principal para 4 servicios: Catalog, Inventory, Reservation, Payment
SQL
Decisión

PostgreSQL 16 en Cloud SQL con HA regional (primary + standby) por servicio. Cada microservicio tiene su propia DB lógica — schema-per-service, no shared database. JSONB para payloads de Event Sourcing. Particionamiento por event_id en tablas de alto volumen.

Comparativa vs alternativas
OpciónProsCons
PostgreSQL Cloud SQL ✓ ACID full. JSONB+GIN. Foreign Data Wrappers. pgvector. Equipo lo domina. Escalado vertical primero. Sharding manual si supera límites.
Cloud Spanner Escalado horizontal automático. Consistencia global externa. SQL. Costo ~10x. Latencia mayor. Sin extensiones (no pgvector).
MongoDB Document store nativo. Sharding built-in. Transacciones multi-doc complejas. Event Sourcing es más natural en SQL.
EventStoreDB Diseñado específico para Event Sourcing. Subscriptions built-in. Operacional separado. Equipo sin experiencia. Lock-in con vendor.
Trade-off explícito

PostgreSQL no escala horizontalmente sin sharding. Aceptable porque cada BC tiene su propia DB y los hot paths usan Redis. Si Inventory supera 100k writes/sec sostenidos, se considerará Citus (sharding) o migrar a Spanner. Por ahora cada DB maneja ~10-20k writes/sec con réplicas de lectura para queries.

Redis Cluster 7 — GCP Memorystore
Cache, bitmaps de asientos, sorted sets de fila, distributed lock, rate limiting
In-memory
Decisión

Redis Cluster 7 en Memorystore con 3 master + 3 replica nodes. AOF persistence + RDB snapshots cada 5 min. Estructuras especializadas por caso de uso: BITMAP para asientos (1 bit por asiento = O(1) check), ZSET para fila virtual, STRING con TTL para reservas temporales, Lua scripts para operaciones atómicas.

Trade-off vs Hazelcast/Memcached
Redis gana porque
  • Estructuras: ZSET, BITMAP, HASH, STREAMS — no solo K/V
  • Lua scripts atómicos (clave para anti-overbooking)
  • Redlock algorithm bien documentado
  • Memorystore es managed: HA, backup, monitoring
  • Keyspace notifications para TTL events
Riesgos asumidos
  • In-memory: si falla cluster completo, hay pérdida de queue state
  • Mitigado con AOF persistence + replica sync
  • PostgreSQL siempre es source of truth — Redis es speed layer
  • Costo de RAM significativo (50k asientos × 5k eventos = ~250MB)
Elasticsearch 8
Búsqueda full-text + faceted + geo queries para Event Catalog (read-side)
Search
Decisión

Elasticsearch 8 en GKE como read-side de Event Catalog. PostgreSQL es source of truth, ES se sincroniza vía Kafka (CDC con Debezium o eventos de dominio). Índices por fecha de evento para hot/cold data separation.

Trade-off vs PostgreSQL full-text + pgvector

Se evaluó usar solo PostgreSQL con tsvector + GIN index para full-text. Funciona para volúmenes bajos pero degrada con relevance scoring complejo y faceted search. Elasticsearch agrega operacional (cluster, mappings, replication), pero gana en: relevance scoring (BM25 customizable), faceted aggregations en milisegundos, autocomplete con edge n-grams, y geo queries con geo_distance. Para 50M DAU haciendo browse intensivo, ES paga su complejidad.

El backbone event-driven es Kafka. Toda comunicación entre bounded contexts es asíncrona por default. Las únicas llamadas sincrónicas (gRPC/REST) son donde la respuesta es necesaria en el critical path: Queue → Inventory (check availability) y Payment → AI (fraud score).
Apache Kafka — Confluent Platform en GKE
Event backbone de todos los bounded contexts
Mensajería
Decisión

Kafka self-hosted en GKE con Strimzi operator. Particionamiento por event_id (garantiza ordenamiento de eventos del mismo evento). Replication factor 3, min.insync.replicas=2. Topics compactos para estado de inventario, time-based retention 7 días para el resto. Exactly-once semantics habilitado con transactional producers en Payment y Reservation.

Trade-off vs GCP Pub/Sub
AspectoKafkaPub/Sub
OrdenamientoGarantizado por partition keySolo con ordering keys (con costo de throughput)

Exactly-onceTransactional producersAt-least-once por default

Decisión híbrida

Kafka para inter-servicios (Reservation Saga, Inventory events, Payment outbox) donde el control fino de ordering, retention y replay es crítico. GCP Pub/Sub para fan-out masivo de notificaciones (apertura de venta: 5M push notifications) donde la simplicidad operacional y el auto-scaling justifican el costo variable. Kafka Streams se usa para agregaciones en tiempo real (tickets/segundo, revenue dashboard).

gRPC para llamadas sincrónicas inter-servicios
REST solo en bordes (clientes externos). gRPC internamente.
RPC
Decisión

REST/JSON en el API Gateway hacia clientes. gRPC con Protocol Buffers para todas las llamadas internas sincrónicas: Queue → Inventory (check availability), Payment → AI (fraud score), Reservation → Catalog (lookup event).

Trade-off

gRPC ofrece ~30% menos latencia que JSON sobre HTTP/1.1 (HTTP/2 multiplexing + binary serialization). Protobuf evita typos y desincronización de contratos. La desventaja es que requiere herramientas extra (protoc, plugins) y debugging menos amigable (no es human-readable). Trade-off aceptable internamente; los clientes externos siguen recibiendo JSON via Gateway transformer.

Multi-cloud strategy. GCP como cloud primario (familiaridad del equipo NFD S.A.). OCI como DR / fallback para componentes críticos. Avoid vendor lock-in usando estándares abiertos (Kubernetes, PostgreSQL, Kafka) — facilita migración entre clouds si es necesario.
GKE Autopilot — Multi-zone us-central1
Orquestación de todos los microservicios
Compute
Decisión

GKE Autopilot multi-zone con HPA (CPU + custom metrics como queue_size). Workers no críticos (Notification, embeddings) en Spot nodes (~50% del costo). PodAntiAffinity para distribución entre zonas. Workload Identity (SA K8s = SA GCP, sin keys).

Trade-off vs GKE Standard / Cloud Run

Cloud Run sería más simple para servicios stateless, pero no soporta WebSocket largo de Virtual Queue ni gestión fina de recursos. GKE Standard da control total de node pools pero requiere expertise operacional para tuning. Autopilot es el sweet spot: GCP gestiona node pools, scaling, security patches; nosotros gestionamos workloads. Pierde el control de instance types específicos — aceptable porque resources.requests bien definidos garantizan que Autopilot asigna instances apropiadas.

Istio Service Mesh
mTLS, traffic management, observabilidad
Mesh
Decisión

Istio (Anthos Service Mesh managed) sobre GKE. mTLS automático entre servicios (zero-trust). VirtualService + DestinationRule para canary deployments (95/5 traffic split). Envoy sidecars inject distributed tracing headers W3C TraceContext automáticamente. OPA via ext_authz filter para policy-based authorization.

Trade-off vs Linkerd / sin mesh

Istio agrega ~5-10ms latency por hop (sidecar Envoy). Memoria adicional ~50MB por pod. Linkerd es más liviano (~2ms, ~20MB) pero tiene menos features (sin OPA integration, sin traffic mirroring avanzado). Sin service mesh, tendríamos que implementar mTLS, retry, tracing manualmente en cada servicio — duplicación masiva. Para 7 microservicios la decisión es clara: Istio paga su overhead con features que el equipo no tendría que mantener.

Spring Cloud Gateway
API Gateway con rate limiting, JWT validation, routing
Gateway
Decisión

Spring Cloud Gateway corriendo en GKE. Rate limiting con Redis backend (sliding window por userId/eventId). JWT validation con Keycloak JWKS cache. Circuit breaker via Resilience4j filter. Path-based routing hacia servicios downstream.

Trade-off vs Kong / Apigee
Spring Cloud Gateway elegido por
  • Stack 100% Java: equipo sabe debuggear
  • Configuration as code (versionado en Git)
  • WebFlux non-blocking: ideal para picos de tráfico
  • Integración nativa con Resilience4j, Micrometer, OAuth2
Sacrificado vs Kong/Apigee
  • Sin admin UI: cambios via deploy
  • Plugin ecosystem menor (pero suficiente con filters custom)
  • Sin developer portal nativo (no es prioridad fase 1)
Defense in depth. Cinco capas: Cloud Armor (WAF/DDoS) → JWT Auth (Keycloak) → mTLS inter-servicio (Istio) → OPA policy (authorization) → Secrets Manager (credenciales). Compliance: PCI-DSS para flujo de pagos (tokenización en frontend, backend nunca ve PAN), GDPR/LGPD para datos personales.
Keycloak (OIDC + OAuth2)
Identity provider con JWT RS256, refresh tokens, MFA
IdP
Decisión

Keycloak self-hosted en GKE con PostgreSQL backend. JWT RS256 (asimétrico — los servicios validan con public key sin necesitar secret compartido). Refresh tokens rotativos. MFA obligatorio para scope payments:write. Federación con providers externos (Google, Apple ID) configurada.

Trade-off vs Auth0 / GCP Identity Platform

Auth0 y Identity Platform son SaaS, cero ops pero costo $0.023+ por MAU activo. Para 50M DAU = ~$1M/mes. Keycloak self-hosted: ~$200/mes infra + tiempo de operación. Trade-off claro: ahorro masivo a costo de gestión operacional. Mitigado con expertise SRE existente en NFD S.A. Backup automático cada 6h, DR en OCI.

OPA (Open Policy Agent)
Authorization declarativa via Rego policies
Authz
Decisión

OPA como sidecar (Envoy ext_authz filter en Istio). Policies en Rego versionadas en Git. Ejemplo: usuario puede ver reservas propias (input.user.id == input.resource.owner_id), admin puede cancelar eventos, MFA requerido para payments.

Trade-off

Alternativa: lógica de authorization embebida en cada servicio (Spring Security). OPA externaliza policy de código — cambios sin redeploys, audit centralizado, policies testeables con OPA test framework. Costo: ~1-2ms latency adicional por request (cached). Trade-off acepta esta latencia por la flexibilidad y auditabilidad.

Cloud Armor + Secret Manager
Edge security + gestión de secretos
Defense
Decisiones

Cloud Armor: WAF con reglas OWASP Top 10, DDoS Adaptive Protection L7, rate limiting por IP, geo-blocking opcional. Absorbe ataques antes del LB. GCP Secret Manager: todas las credenciales (DB passwords, Stripe API key, JWT signing key) en Secret Manager con rotación automática. Aplicaciones consumen via Workload Identity, nunca como env vars planos en YAML.

SRE como ciudadano de primera clase. Los tres pilares (métricas, logs, tracing) están desde el día 1. SLOs definidos antes de production. Error budget burn rate alerts. Esto reutiliza el stack Grafana ya operacional en NFD S.A.
Prometheus + Grafana + Alertmanager
Métricas y dashboards. SLO burn rate alerts.
Metrics
Decisión

Prometheus federado (un Prometheus por GKE cluster + un global aggregator). Grafana para visualización — dashboards por servicio + SLO dashboard global. Alertmanager con integración PagerDuty. SLOs definidos: search p99 < 200ms, checkout p99 < 500ms, queue join p99 < 100ms, availability 99.9% mensual.

Trade-off vs Google Cloud Operations

Google Cloud Operations (ex Stackdriver) está integrado y serverless. Pero Grafana es portable entre clouds (NFD S.A. tiene workloads en OCI también). Prometheus es OSS estándar. Trade-off: gestión operacional adicional vs portabilidad y consistencia entre clouds. Long-term storage: Prometheus retiene 15 días, exporta a BigQuery via Grafana datasource para análisis histórico (compliance, capacity planning).

OpenTelemetry + Google Cloud Trace
Distributed tracing W3C TraceContext, auto-instrumentación
Tracing
Decisión

OpenTelemetry Java Agent (auto-instrumentación de Spring, JDBC, Kafka, HTTP clients). Sampling: 100% en errores, 10% en éxito (head-based sampling), 100% en checkout flow. Exportador hacia Google Cloud Trace (managed, sin operar Jaeger). Trace ID propagado en logs y respuestas HTTP (header X-Trace-Id) para correlación.

Trade-off

Alternativa Jaeger self-hosted: control total pero ops. Cloud Trace managed: integrado con GCP, retention 30 días, query rápido. Costo: $0.20 por millón de spans — barato a escala. OpenTelemetry es vendor-neutral, si en el futuro se migra a otro backend (Datadog, Honeycomb), el código de instrumentación no cambia.

Cloud Logging — Structured JSON logs
Centralizado, correlacionado con trace ID, exportado a BigQuery
Logs
Decisión

Logback con Logstash JSON encoder. Cada log incluye trace_id, span_id, user_id, event_id cuando aplica. Cloud Logging captura stdout de pods automáticamente. Log-based metrics para alerting (ej: alertar si level=ERROR AND service=payment > 10/min). Export a BigQuery para análisis ad-hoc con SQL.

Spring AI como abstracción. Spring AI 1.x estandariza la integración con LLMs (Gemini, OpenAI, Anthropic), embeddings y vector stores. Esta capa de abstracción permite cambiar de provider sin reescribir lógica de negocio.
Spring AI 1.x + Vertex AI Gemini Pro
ChatClient, ChatMemory, VectorStore, Advisors (RAG), Function Calling
LLM
Decisión

Spring AI con spring-ai-vertex-ai-gemini-spring-boot-starter. Gemini 1.5 Pro como modelo principal (1M token context, excelente para RAG). QuestionAnswerAdvisor para RAG automático sobre pgvector. ChatMemory via PostgreSQL para sessions multi-turn. Function Calling para que el LLM pueda invocar tools (ej: getEventDetails(id), checkAvailability(eventId)).

Por qué Spring AI

Si mañana cambiamos a Claude o GPT-5, solo cambiamos el starter en Maven — la lógica de negocio (ChatClient, advisors) permanece igual. Spring AI estandariza vendor-neutral. Para una arquitectura que debe sobrevivir 5+ años, esta abstracción es crítica.

pgvector + HNSW index
Vector store para embeddings de eventos (dim 768)
Vector DB
Decisión

pgvector extension sobre PostgreSQL existente (ai_db). Embeddings generados por text-embedding-004 (768 dim). Índice HNSW (Hierarchical Navigable Small World) con ef_construction=128, m=16. Búsqueda por similitud coseno con filtros pre-retrieval via JSONB metadata.

Trade-off vs Pinecone / Weaviate / Vertex AI Vector Search

Pinecone/Weaviate son vector DBs especializados, scaling horizontal nativo, latencia <5ms a 1B vectors. Vertex AI Vector Search es managed por GCP. pgvector ganó por: reutiliza infra Postgres existente (sin nuevo componente operacional), transacciones ACID (embedding y metadata atómicos), costo cero adicional. Trade-off explícito: pgvector escala bien hasta ~10M vectors con HNSW; si superamos eso, migración a Vertex AI Vector Search planeada (Spring AI lo abstrae).

Resilience4j en cada operación crítica. Circuit Breaker, Retry, Bulkhead, TimeLimiter, RateLimiter. Configurado declarativamente con annotations. Métricas exportadas a Prometheus para visibilidad. Default: fail fast con fallback inteligente.

Trade-off vs Hystrix / Sentinel

Hystrix está en maintenance mode desde 2018. Sentinel (Alibaba) es potente pero ecosystem chino, menos community en occidente. Resilience4j es el sucesor de facto en JVM: lightweight, Java 8+, modular (incluyes solo lo que usás), integrado con Micrometer. Decisión obvia para el stack.

Patrones de consistencia distribuida
Saga coreografiado + Outbox + Idempotency Keys
Patterns
Decisiones

Saga coreografiado (no orquestado): cada servicio reacciona a eventos sin orquestador central. Menos acoplamiento pero más complejo de debuggear. Mitigado con OpenTelemetry tracing. Outbox Pattern: garantiza que eventos publicados a Kafka están en sync con commits a DB. Sin outbox, riesgo de "DB commited pero Kafka falló" rompe la consistencia eventual. Idempotency Keys: header X-Idempotency-Key en operaciones no idempotentes (payment, reservation). Server cachea respuesta por 24h.

Por qué coreografiado y no orquestado

Saga orquestado (con un Saga Coordinator central, ej. Camunda/Temporal) simplifica debugging y visibilidad del flujo. Pero introduce single point of coupling: el coordinator conoce todos los pasos. Para escalado y evolución independiente de cada BC, coreografiado gana. Trade-off: debugging vía traces distribuidos requiere mejor instrumentación — invertido en OpenTelemetry para compensar.
